Week 2 Lab — Trace, Delegate, Cut Over, and Speak HTTP

35 minutes. Work individually, on your domain or assigned course subdomain.

Commands start at the course content root (student release; instructor for authors). Continue web foundations steps 4–6 within the HW2 work budget; this is not extra prep.

Setup happens before class, not during it — see the checklist below. The 35 minutes is 7 + 4 + 7 + 9 + 6, plus two minutes of slack.

What you leave with. A dig +trace transcript, a working record in a zone you control, a measured TTL countdown, an executed cutover with a rollback, and an HTTP request you typed with your own hands. Four of the five are HW2 evidence — save everything.

Part 1 — Trace the delegation from the root (7 min)

You are going to watch a resolver do its job, one referral at a time.

1.1 The whole path in one command

dig +trace depaul.edu A

Expected shape — four groups, each ending in a ;; Received … from line:

.             518400  IN  NS  a.root-servers.net.        <- root hints
;; Received … from 1.1.1.1#53(1.1.1.1)

edu.          172800  IN  NS  a.edu-servers.net.         <- root referral
;; Received … from 192.203.230.10#53(e.root-servers.net)

depaul.edu.   172800  IN  NS  ns1.depaul.edu.            <- edu referral
;; Received … from 192.5.6.30#53(a.edu-servers.net)

depaul.edu.    86400  IN  A   64.239.109.1               <- the answer
;; Received … from 140.192.141.178#53(ns3.depaul.edu)

Record in your file: which server answered each of the four groups.

If it stalls after the first group, try dig -4 +trace depaul.edu A. Missing IPv6 reachability is one hypothesis; direct DNS filtering, packet loss or an unreachable authority are others. Use the fallback rather than infer a cause.

1.2 Now do it by hand, one hop at a time

Run these three. Each one asks a different server the same question.

dig @a.root-servers.net depaul.edu A +norecurse
dig @a.edu-servers.net  depaul.edu A +norecurse
dig @ns1.depaul.edu     depaul.edu A +norecurse

Record for each: the flags: line and the ANSWER: count.

ServerExpected flagsExpected ANSWER:
Rootqr0 — a referral
TLDqr0 — a referral
Authoritativeqr aa1 — the answer

+norecurse is what makes this readable. Without it, dig sets rd and the root and TLD servers simply do not offer recursion — you get the same referral, but with an extra flag muddying the comparison.

✅ Checkpoint 1. In your file, write one sentence answering: which of those three servers set the aa flag, and what does that flag entitle you to conclude?

Part 2 — Recursive vs authoritative, and the age of a cache (4 min)

2.1 Ask a recursive resolver the same question

dig @1.1.1.1 depaul.edu A

Compare its header to the authoritative one from 1.2:

Recursive (@1.1.1.1)Authoritative (@ns1.depaul.edu)
Flagsqr rd raqr aa
TTLbelow 86400, fallingexactly 86400, always

2.2 Measure how old that cache entry is

Read the authoritative TTL in the same session — do not assume the configured value is the value being served.

authoritative 86400 − resolver-reported 85555 = ~845 s since that cache refreshed

Record: your own subtraction, with both numbers, and call it an apparent cache age — resolvers may cap, prefetch, or serve stale.

2.3 Prove a cache exists without changing anything

dig @1.1.1.1 example.com A +norecurse

You asked a recursive resolver not to recurse. If it answers anyway, the answer came from its cache. If it returns ANSWER: 0, the name was not cached and it declined to go find out.

✅ Checkpoint 2. Run dig @1.1.1.1 depaul.edu A three times in a row. Do the TTLs decrease monotonically? Write down what you see. (They may not — 1.1.1.1 is an anycast address and consecutive queries can land on different cache nodes. Either result is correct; the observation is the point.)

Part 3 — Configure your own zone and watch a TTL expire (7 min)

Continue working on your own domain — the one you configured in HW1.

Never share your DNS credentials with anyone, including classmates.

You should already be logged in to your DNS host — it was on the pre-class checklist. If you are not, log in now before continuing.

3.1 Find out who is authoritative for your domain

dig NS yourdomain.example +short
dig SOA yourdomain.example +short

The NS answer names your DNS host. If it is not the company you think is hosting your DNS, you have been editing a zone nobody consults.

Do not try to fix delegation during the lab. Changing nameservers is a change with a two-day parent TTL; it cannot complete in 35 minutes. Use the instructor's fallback subdomain for Parts 3 and 4 instead, note the finding in your file, and repair your own domain after class.

3.2 Create one record

In your DNS host's console, create:

NameTypeValueTTLProxy
labA203.0.113.1060DNS only / unproxied

203.0.113.0/24 is an RFC 5737 documentation range, not a deployment target. This is a DNS-only exercise; do not send application traffic to it.

Cloudflare users: grey cloud, not orange. A proxied record ignores your TTL, reports Auto, and returns Cloudflare's own addresses instead of yours — so every measurement in Parts 3 and 4 would be of something you did not configure. Any proxying host behaves the same way.

If your host will not accept a TTL of 60, use its minimum and record it. Keep the 35-minute lab cap: start the change here and finish the timed observation in HW2, or use supplied countdown/cutover evidence with honest provenance.

Do not query this name before you create it. A lookup for a name that does not exist yet installs a negative cache entry, and you will then wait out the SOA negative TTL before your new record becomes visible. This is the single most common way to lose ten minutes in this lab.

3.3 Verify from the authoritative server first

dig +trace lab.yourdomain.example A

+trace walks the delegation from the root and never consults a recursive cache for your name, so it shows you the truth immediately. (Its first query — the root nameserver list — does go to your configured resolver; everything after that is direct.) If this does not show your record, the record is wrong — not cached.

Note the TTL that +trace reports: it is 60, the zone value, every time. Authoritative answers normally report the configured TTL; synthesized/provider answers can differ. Record what yours serves rather than force the example number.

3.4 Watch the TTL count down

dig @1.1.1.1 lab.yourdomain.example A +noall +answer
# wait 20 seconds
dig @1.1.1.1 lab.yourdomain.example A +noall +answer
# wait 20 seconds
dig @1.1.1.1 lab.yourdomain.example A +noall +answer
# wait 25 seconds — past expiry
dig @1.1.1.1 lab.yourdomain.example A +noall +answer

Expected: 60 → roughly 40 → roughly 20 → back to 60 after it expires and the resolver re-fetches.

Record: the sequence, with timestamps.

✅ Checkpoint 3. Write one sentence: if this record had a TTL of 3600 instead, and you had to change it in five minutes, what would you have needed to do an hour ago?

Part 4 — Execute a cutover with a rollback (9 min)

You have a record at TTL 60. That is a deliberately open rollback window. Use it.

4.1 Write the plan before you touch anything

Copy this into your file and fill it in:

CUTOVER PLAN — lab.yourdomain.example
  Current value : 203.0.113.10        <- write this down first. This is your rollback.
  New value     : 198.51.100.20
  Current TTL   : 60  (lowered at HH:MM, already in effect)
  Change at     : HH:MM
  Verify by     : dig @1.1.1.1 ... and dig @8.8.8.8 ... and dig +trace ...
  Success means : both resolvers return 198.51.100.20
  Rollback if   : either resolver still returns the old value after 3 minutes
  Rollback = restore 203.0.113.10; expected live within 60 s

4.2 Capture the before-state

dig @1.1.1.1 lab.yourdomain.example A +noall +answer
dig @8.8.8.8 lab.yourdomain.example A +noall +answer

4.3 Make the change

Change lab to 198.51.100.20. Note the wall-clock time. Change nothing else.

Timestamps: date -u on macOS/Linux/WSL. In PowerShell use (Get-Date).ToUniversalTime().ToString('HH:mm:ss') + 'Z'.

4.4 Verify from two independent resolvers plus the source of truth

dig @1.1.1.1 lab.yourdomain.example A +noall +answer
dig @8.8.8.8 lab.yourdomain.example A +noall +answer
dig +trace   lab.yourdomain.example A | tail -n 5

Windows PowerShell: tail is an alias for Get-Content and will reject -n 5. Use dig +trace lab.yourdomain.example A | Select-Object -Last 5 instead.

Repeat every 30 seconds until both public resolvers show the new value. Record how long it took.

4.5 Roll back

Restore 203.0.113.10. Verify the same three ways. Record how long the rollback took.

✅ Checkpoint 4. You now have a measured rollback time. Write it down — HW2 asks you to defend a TTL choice, and this number is the defence.

What if +trace shows the new value but the resolvers do not? That is the correct, expected intermediate state, and it is the whole lesson: the authoritative data changed instantly; the caches have not expired yet. Nothing is propagating.

Part 5 — Speak HTTP with your hands (6 min)

5.1 Start the fault server

From the repository root:

node weeks/week02/samples/http-faults/fault-server.mjs

The path is relative to the repo root. If you are elsewhere, cd there first or give an absolute path.

Expected:

fault1 listening on http://127.0.0.1:8081
fault2 listening on http://127.0.0.1:8082
fault3 listening on http://127.0.0.1:8083
fault3-lb listening on http://127.0.0.1:8084

Leave it running. Open a second terminal.

5.2 Write an HTTP request by hand

macOS / Linux / WSL:

printf 'GET /healthz HTTP/1.1\r\nHost: status.campuspulse.example\r\nConnection: close\r\n\r\n' \
  | nc 127.0.0.1 8081

Connection: close matters. HTTP/1.1 keeps the socket open by default. Without that header, nc prints the response and then sits there until the server times out.

Windows PowerShell (no nc required):

$c = [Net.Sockets.TcpClient]::new('127.0.0.1', 8081)
$s = $c.GetStream()
$req = "GET /healthz HTTP/1.1`r`nHost: status.campuspulse.example`r`nConnection: close`r`n`r`n"
$b = [Text.Encoding]::ASCII.GetBytes($req); $s.Write($b, 0, $b.Length); $s.Flush()
$sr = [IO.StreamReader]::new($s)
while ($null -ne ($line = $sr.ReadLine())) { $line }
$c.Close()

Expected:

HTTP/1.1 200 OK
Server: campuspulse-fault-lab/1.0
Content-Type: application/json
Content-Length: 39
Vary: Accept-Encoding

{"status":"ok","service":"campuspulse"}

5.3 Change one header value

Run it again with Host: www.campuspulse.example.

Windows: re-run the whole PowerShell block from $c = .... The socket was closed by $c.Close(), so editing $req and writing again throws Cannot access a disposed object. That is not a bug — it is Connection: close doing exactly what you asked for.

Expected: HTTP/1.1 404 Not Found and X-Served-By: shared-edge-7.

Same address. Same port. Same bytes except one header value. DNS was never involved.

✅ Checkpoint 5. Write one sentence explaining why a 404 here would not be fixed by any change to a DNS record.

Troubleshooting

1. dig +trace hangs or says "no servers could be reached"

Two different failures wear the same message. Tell them apart by where it stops.

(a) It prints the root NS list, then stalls. IPv6 reachability or direct UDP/TCP 53 filtering are hypotheses, not diagnoses from this symptom alone.

dig -4 +trace depaul.edu A          # force IPv4 for the whole walk

(b) It fails immediately, before printing anything. +trace starts by asking your configured resolver for the root nameserver list, and yours refused or timed out. Common on WSL, on VPNs, and behind captive portals. Name a starting resolver:

dig -4 @1.1.1.1 +trace depaul.edu A

If both fail, port 53 is being blocked or intercepted. Confirm the network is otherwise fine using DoH, which rides on 443:

curl -s -H "accept: application/dns-json" \
  "https://cloudflare-dns.com/dns-query?name=depaul.edu&type=A"

If that works and dig does not, direct DNS filtering is one hypothesis. Note the observation — it is a legitimate observation, not a failure, and it is exactly the DoH operational effect from Block A.

2. Your new record returns NXDOMAIN from a resolver but +trace shows it

Cause: negative caching. Something queried the name before it existed, and the resolver cached the NXDOMAIN.

dig @1.1.1.1 lab.yourdomain.example A     # read the SOA in the AUTHORITY section

The negative-cache lifetime is the lesser of that SOA record's own TTL and its minimum field — the last number in the SOA RDATA (RFC 2308 §5). Read both; take the smaller.

Wait that many seconds. Do not "fix" the record — it is already correct. Record this in your notes; it is exactly the evidence HW2 wants for a deliberate failure.

3. The TTL does not decrease between queries to 1.1.1.1

Cause: 1.1.1.1 is not one server. It is a distributed service — many sites, each with its own cache, and load balancing within each site. You are reaching different cache state, not one countdown.

for i in 1 2 3 4 5 6; do dig @1.1.1.1 depaul.edu A +noall +answer; done

Different TTLs are consistent with different cache nodes, refresh or prefetch; they do not uniquely prove anycast routing. On an unmanaged practice machine, you may inspect your own OS cache for a clean monotonic countdown instead:

Clear-DnsClientCache
Resolve-DnsName lab.yourdomain.example -Type A | Out-Null
1..6 | ForEach-Object {
  Get-DnsClientCache -Entry lab.yourdomain.example | Where-Object Type -eq 1 |
    Select-Object -First 1 Entry, TimeToLive, Data
  Start-Sleep 5
}

# Linux with systemd-resolved
resolvectl flush-caches && resolvectl query lab.yourdomain.example

4. node fault-server.mjs fails with EADDRINUSE

Another process holds 8081–8084. Start it somewhere else:

node weeks/week02/samples/http-faults/fault-server.mjs --port 9100

Then use 9100–9103 in place of 8081–8084.

For independently allocated ports, run the same server with --port 0. Read the reported PORTS mapping (fault1, fault2, fault3, proxy) and substitute each actual port separately; do not calculate them by adding to the first one. This is the preferred mode for parallel automated tests.
